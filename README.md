# YamDelish

YamDelish — учебное веб-приложение службы доставки еды. Проект показывает полный пользовательский путь: просмотр ресторанов, переход в меню, добавление блюд в корзину, оформление заказа, просмотр истории заказов, оценка доставки и работа с профилем пользователя.

Приложение построено на строгом стеке:

- Next.js
- React
- Tailwind CSS
- Drizzle ORM
- Turso Database / libSQL
- SQLite для локальной разработки
- Vitest для unit-тестов backend-кода

## Назначение Проекта

Основная цель проекта — реализовать рабочий frontend и backend для сервиса доставки еды без моковых JSON-заглушек во фронтенде. Данные ресторанов, меню, корзины, заказов, профиля и отзывов приходят через API-роуты Next.js и сохраняются в базе данных через Drizzle ORM.

Локально проект запускается без Turso: используется SQLite-файл `sqlite.db`, который автоматически создаётся и наполняется тестовыми данными при запуске `npm run dev`.

Для production или удалённой разработки можно подключить Turso через переменные окружения.

## Основные Возможности

### Главная Страница

Главная страница отображает список ресторанов из backend API. Для каждого ресторана выводятся:

- название;
- изображение;
- рейтинг;
- тип кухни;
- описание;
- время доставки;
- средний чек;
- признак избранного;
- признак недавнего заказа.

Данные загружаются через endpoint:

```http
GET /api/restaurants
```

### Фильтрация Ресторанов

На главной странице есть фильтры по:

- типу кухни;
- рейтингу;
- времени доставки.

Фильтры работают на клиентской стороне поверх данных, полученных из backend.

### Страница Меню

Страница меню открывается для конкретного ресторана. Блюда загружаются по `restaurantId`:

```http
GET /api/menu?restaurantId=10000000-0000-4000-8000-000000000001
```

Блюда группируются по категориям, например:

- Супы;
- Основные блюда;
- Десерты;
- Напитки.

Пользователь может добавить блюдо в корзину. Добавление выполняется через backend:

```http
POST /api/cart
```

### Корзина

Корзина показывает блюда текущего тестового пользователя. Для локальной разработки этот пользователь создаётся seed-скриптом с UUID-идентификатором.

Корзина поддерживает:

- просмотр позиций;
- изменение количества;
- удаление позиции;
- расчёт общей суммы;
- оформление заказа.

Используемые endpoints:

```http
GET /api/cart
POST /api/cart
PATCH /api/cart
DELETE /api/cart?cartItemId=...
```

### Оформление Заказа

Кнопка `Оформление заказа` на странице корзины создаёт заказ из текущих позиций корзины.

Запрос:

```http
POST /api/orders
```

После успешного оформления:

- создаётся запись в `orders`;
- создаются записи в `order_items`;
- цена каждого блюда фиксируется в `price_at_order`;
- корзина пользователя очищается;
- пользователь перенаправляется на страницу деталей созданного заказа.

Если фронтенд не передал адрес доставки, backend берёт адрес из профиля пользователя. Это сделано для локального демонстрационного сценария, чтобы оформление заказа работало без отдельной формы доставки.

### История Заказов

Страница истории заказов загружает реальные заказы пользователя:

```http
GET /api/orders
```

Каждая карточка заказа содержит:

- дату;
- время;
- ресторан;
- сумму;
- статус;
- кнопку перехода к деталям.

### Детали Заказа

Страница деталей заказа открывается по id:

```http
GET /api/orders/:id
```

На странице отображаются:

- дата и время заказа;
- статус;
- ресторан;
- список блюд;
- количество блюд;
- цена на момент заказа;
- итоговая сумма;
- адрес доставки;
- способ оплаты;
- данные курьера;
- форма оценки заказа.

### Оценка Заказа

Пользователь может поставить оценки ресторану и доставке, а также оставить текстовый отзыв.

Запрос:

```http
POST /api/orders/rating
```

Оценка хранится в таблице `order_ratings`. Для одного заказа допускается только одна оценка. Повторная отправка отклоняется с ответом `409 Conflict`.

### Профиль Пользователя

Профиль пользователя загружается из backend:

```http
GET /api/users/00000000-0000-4000-8000-000000000001
```

Пользователь может изменить:

- имя;
- фамилию;
- телефон;
- адрес.

Сохранение профиля:

```http
PATCH /api/users/00000000-0000-4000-8000-000000000001
```

### Авторизация И Регистрация

В проекте есть базовые endpoints:

```http
POST /api/auth/register
POST /api/auth/login
POST /api/password/restore
```

Пароли не сохраняются открытым текстом. Для хеширования используется встроенный Node.js `crypto.scrypt`.

Тестовый пользователь:

```text
Email: guest@yamdelish.local
Password: password123
```

## Архитектура

Проект использует Pages Router в Next.js.

Основные директории:

```text
src/
  api/                 Клиентские функции для обращения к backend
  components/          React-компоненты интерфейса
  db/                  Drizzle schema, подключение к БД и seed
  services/            Бизнес-логика, DTO и операции Drizzle ORM
  models/              Zod-модели для форм и доменных сущностей
  pages/               Next.js pages и API routes
  styles/              Глобальные стили Tailwind
  types/               TypeScript-типы frontend/backend контрактов
  utils/               Утилиты проекта
tests/
  backend/             Unit-тесты backend API и DTO
migrations/
  *.sql                SQL-миграции Drizzle
```

## Backend

Backend реализован через API routes Next.js в директории:

```text
src/pages/api/
```

API routes не работают напрямую с SQL. Основная логика вынесена в:

```text
src/services/delivery.ts
src/services/auth.ts
```

Такой подход нужен, чтобы:

- держать API handlers тонкими;
- переиспользовать логику между routes;
- проще покрывать код unit-тестами;
- отделить HTTP-контракт от работы с базой.

## Database

Схема базы данных описана в:

```text
src/db/schema.ts
```

Подключение к базе:

```text
src/db/index.ts
```

Drizzle config:

```text
drizzle.config.ts
```

Локально используется:

```text
file:sqlite.db
```

Для Turso используются переменные окружения:

```env
TURSO_DATABASE_URL=libsql://...
TURSO_AUTH_TOKEN=...
```

Если переменные не указаны, приложение автоматически работает с локальной SQLite-базой.

Защищённые API по умолчанию определяют пользователя только по подписанной cookie-сессии. Для
специального демонстрационного режима можно явно установить `ALLOW_DEMO_AUTH=true`; тогда
допускается тестовый `userId` из query-параметра.

Контрольный замер API выполняется командой `npm run benchmark:api`. Скрипт делает пять запросов
для ресторанов, меню, корзины, оформления заказа, истории и деталей заказа, после чего выводит
среднее время, p50 и p95 в JSON. Для авторизации нужно передать `BENCHMARK_SESSION_COOKIE` либо
пару `BENCHMARK_EMAIL` и `BENCHMARK_PASSWORD`. Созданные тестовые заказы перечисляются в поле
`createdOrderIds`, чтобы их можно было удалить после замера.
Последний сохранённый локальный результат находится в каталоге `benchmarks/`.

## Схема Базы Данных

### users

Таблица пользователей.

Поля:

- `id` — идентификатор пользователя;
- `name` — имя;
- `surname` — фамилия;
- `email` — уникальный email;
- `password_hash` — хеш пароля;
- `phone` — телефон;
- `address` — адрес доставки;
- `created_at` — дата создания;
- `updated_at` — дата обновления.

Связи:

- один пользователь имеет много позиций корзины;
- один пользователь имеет много заказов.

### restaurants

Таблица ресторанов.

Поля:

- `id`;
- `name`;
- `description`;
- `kitchen_type`;
- `delivery_time_from`;
- `delivery_time_to`;
- `average_check_from`;
- `average_check_to`;
- `rating`;
- `image`;
- `recent`;
- `favorite`;
- `created_at`;
- `updated_at`.

Связи:

- один ресторан имеет много блюд;
- один ресторан имеет много заказов.

### dishes

Таблица блюд.

Поля:

- `id`;
- `restaurant_id`;
- `name`;
- `description`;
- `image`;
- `group_name`;
- `price`;
- `created_at`;
- `updated_at`.

Связи:

- блюдо принадлежит ресторану;
- блюдо может быть в корзине;
- блюдо может быть в позициях заказа.

### cart_items

Таблица позиций корзины.

Поля:

- `id`;
- `user_id`;
- `dish_id`;
- `quantity`;
- `created_at`;
- `updated_at`.

Особенности:

- есть уникальный индекс `user_id + dish_id`;
- повторное добавление блюда увеличивает количество, а не создаёт дубль.

### orders

Таблица заказов.

Поля:

- `id`;
- `user_id`;
- `restaurant_id`;
- `status`;
- `address`;
- `courier_name`;
- `courier_phone`;
- `payment_method`;
- `payment_status`;
- `total_price`;
- `created_at`;
- `updated_at`.

Статусы:

- `created`;
- `cooking`;
- `delivering`;
- `delivered`;
- `canceled`.

### order_items

Таблица позиций заказа.

Поля:

- `id`;
- `order_id`;
- `dish_id`;
- `quantity`;
- `price_at_order`.

Поле `price_at_order` фиксирует цену блюда на момент оформления заказа. Благодаря этому история заказа не меняется, если цена блюда позже будет изменена в меню.

### order_ratings

Таблица оценок заказов.

Поля:

- `id`;
- `order_id`;
- `restaurant_rating`;
- `delivery_rating`;
- `feedback`;
- `created_at`.

Для одного заказа может быть только одна оценка.

## Локальные Тестовые Данные

Seed находится в:

```text
src/db/seed.ts
```

Он создаёт:

- тестового пользователя;
- рестораны;
- блюда;
- корзину;
- заказы с разными статусами;
- позиции заказов;
- оценку заказа.

Seed можно запускать повторно. Он использует фиксированные id и `onConflictDoNothing` / `onConflictDoUpdate`, поэтому повторный запуск не ломает базу дублями.

## Запуск Проекта

### Запуск через Docker

Для запуска приложения вместе с локальной SQLite-базой достаточно выполнить одну команду:

```bash
docker compose up --build
```

После сборки приложение доступно по адресу:

```text
http://localhost:3000
```

Для проверки пользовательских сценариев войдите под тестовой учётной записью:

```text
Email: guest@yamdelish.local
Пароль: password123
```

При старте контейнер автоматически применяет миграции Drizzle и наполняет базу тестовыми
данными. Файл SQLite хранится в именованном Docker volume `yamdelish_data`, поэтому данные
сохраняются после остановки и повторного создания контейнера.

Полезные команды:

```bash
# Запустить в фоновом режиме
docker compose up --build -d

# Посмотреть логи
docker compose logs -f app

# Остановить приложение
docker compose down

# Остановить приложение и удалить локальную базу
docker compose down -v
```

Если порт `3000` занят, можно выбрать другой порт на компьютере:

```bash
APP_PORT=3001 docker compose up --build
```

Для подключения удалённой Turso вместо локальной SQLite создайте файл `.env` рядом с
`compose.yaml`:

```env
TURSO_DATABASE_URL=libsql://your-database.turso.io
TURSO_AUTH_TOKEN=your-token
AUTH_SECRET=replace-with-a-long-random-secret
SESSION_COOKIE_SECURE=true
```

Docker Compose автоматически прочитает этот файл. Не добавляйте `.env` в Git. Значение
`AUTH_SECRET`, заданное в `compose.yaml` по умолчанию, предназначено только для локального
демонстрационного запуска; для общего стенда или production задайте собственный длинный
случайный секрет.

Для локального Docker-запуска по HTTP параметр `SESSION_COOKIE_SECURE` автоматически равен
`false`, чтобы браузер сохранял cookie авторизации. При развёртывании приложения за HTTPS
установите `SESSION_COOKIE_SECURE=true`.

## Важные Технические Решения

### Почему Есть демонстрационный пользователь

Проект использует подписанную httpOnly session cookie. Демонстрационный пользователь создаётся seed-скриптом с UUID и позволяет войти в локальное приложение с тестовыми учётными данными.

### Почему SQLite Локально И Turso Удалённо

Turso использует libSQL, совместимый с SQLite. Поэтому локальный режим через `file:sqlite.db` максимально близок к удалённой базе Turso и удобен для разработки.

### Почему DTO Вынесены В сервисный слой

Фронтенд ожидает данные в удобном для UI формате:

- цена как строка с валютой;
- диапазон доставки как строка;
- русская подпись статуса;
- рассчитанная цена позиции заказа.

DTO-функции изолируют эти преобразования от компонентов и API handlers.

### Почему Цена Дублируется В order_items

Цена блюда может измениться в меню. История заказа должна оставаться неизменной, поэтому цена на момент оформления сохраняется в `price_at_order`.

### Почему Заказ Создаётся Из Корзины

Корзина является источником состава заказа. При оформлении backend читает текущие `cart_items`, создаёт `orders`, создаёт `order_items`, затем очищает корзину.

## Известные Ограничения

- Нет разделения корзины по нескольким ресторанам.
- Нет административного интерфейса управления ресторанами и меню.
- Нет реальной отправки письма восстановления пароля.
- Нет платёжного провайдера.
- Нет расширенных production-механизмов OAuth, 2FA и rate limiting.

Эти ограничения не мешают локальной демонстрации полного пользовательского сценария доставки еды.

## Основные Пользовательские Сценарии

### Просмотр Ресторанов

1. Пользователь открывает главную страницу.
2. Frontend вызывает `GET /api/restaurants`.
3. Backend читает таблицу `restaurants`.
4. Пользователь видит карточки ресторанов.

### Добавление Блюда В Корзину

1. Пользователь открывает меню ресторана.
2. Frontend вызывает `GET /api/menu?restaurantId=...`.
3. Пользователь нажимает кнопку добавления.
4. Frontend вызывает `POST /api/cart`.
5. Backend создаёт или обновляет позицию корзины.

### Оформление Заказа

1. Пользователь открывает корзину.
2. Frontend вызывает `GET /api/cart`.
3. Пользователь нажимает `Оформление заказа`.
4. Frontend вызывает `POST /api/orders`.
5. Backend создаёт заказ и позиции заказа.
6. Backend очищает корзину.
7. Frontend открывает страницу деталей заказа.

### Оценка Заказа

1. Пользователь открывает детали заказа.
2. Пользователь выбирает оценки и вводит отзыв.
3. Frontend вызывает `POST /api/orders/rating`.
4. Backend создаёт запись в `order_ratings`; повторная отправка отклоняется.
